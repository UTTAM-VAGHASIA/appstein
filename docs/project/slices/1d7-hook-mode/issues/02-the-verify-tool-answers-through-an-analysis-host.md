# The `verify` tool answers through an analysis host

**What to build:** the tracer bullet for the **analysis host** (decision record 0002). The `appstein` binary gains a hidden host mode that owns the project's guard and analysis server and answers code questions over loopback TCP, behind a secret only the user's own processes can read. When a `verify` tool call of `appstein mcp` needs the code analysis and no host answers, it starts one as a detached process, waits for it, and asks it. The host ends itself after 10 minutes with no questions. An agent sees the same findings as before; the server now lives in the host instead of in `appstein mcp`.

**Blocked by:** 01.

Status: resolved

- [x] **First, the platform is proven before anything is built on it:** in the compiled binary, a loopback TCP server on `127.0.0.1` with a port the system picks and a client that sends the secret first, and a detached process started without a console window appearing that reaches the server after its starter has ended, each work on Windows, macOS and Linux in CI. On a real Windows machine, listening on `127.0.0.1` raises no firewall question. Nothing here opens a Unix domain socket: one crashed Windows itself on the owner's machine (decision record 0002). If anything fails, stop and report to the owner before going on.
- [x] The address file (port, secret, process ID, Appstein version) is in a folder of the user's (`%LOCALAPPDATA%\appstein\` on Windows; `$XDG_RUNTIME_DIR`, else the temporary folder, on Linux and macOS), readable by the user only, named by a hash of the project root's full path, and written whole or not at all. A connection that doesn't send the secret first is closed.
- [x] The messages are Appstein's own small protocol, defined in `appstein_protocol`, carrying the questions and answers of the code analysis interface 1d.2 built. The host's client is one more implementation of that interface; the checks don't change.
- [x] The host keeps 1d.2's server rules: the project SDK's server behind the guard, the restarts after a change to the analysis options, the package config or `pubspec.yaml`, the 180 s start limit, the plugin and readiness rules, the barrier that keeps a reading from being older than the files, and `--apply`'s writes (atomic, files outside the project or changed since the reading left alone).
- [x] Starting `appstein mcp` starts no host. The first `verify` call starts one and answers; later calls use it without a new start; an edit between two calls shows in the second.
- [x] The host ends itself after 10 minutes with no questions (one named constant a test can shorten), never during a question. The next `verify` call starts a new one.
- [x] A killed host takes its guard and server with it, and the guard cleans up (ticket 01). `appstein mcp` ending no longer ends the server: the host does, when idle.
- [x] A host that can't start, dies or doesn't answer is Appstein failing, as in 1d.2: an error reply with the reason and "run `appstein doctor`"; the MCP server keeps running.
- [x] The tool's findings equal a terminal run's on the same project state.
- [x] Tests give each host its own address-file folder and cache folder, and no host, guard or server is left running after a test, on Windows too.
- [x] The guide pages for the MCP server, the verifier and the analysis code describe the host; the guide check passes.

## Comments

**2026-10-17, the platform proof.**

- **Unix domain socket: rejected.** The first probe (a compiled Dart program binding a Unix domain socket, connecting and closing) crashed the owner's Windows twice, in Windows' own driver (`afunix.sys`, bugcheck 0xD1, fault bucket `AV_afunix!AfUnixTlConnectEndpointDisconnect`, Windows build 26300). It never ran in CI. The owner chose loopback TCP on all three systems (decision record 0002, commit d53aab0).
- **Loopback TCP: proven.** A throwaway probe (a compiled program; never merged) ran on the owner's Windows and in CI run 38981409417 on Windows, Linux and macOS (Dart 3.13.4), and on the minimum SDK (Dart 3.12.2, Linux). On each: the server bound `127.0.0.1` at a port the system picked; the address file (port, secret, process ID, version) was written whole by a rename, in `%LOCALAPPDATA%\appstein\`, `/run/user/<uid>/appstein/` (Linux) or the temporary folder (macOS), with folder mode 700 and file mode 600 off Windows; the client that sent the secret first got its answer, and one with a wrong secret got none; a child started with `ProcessStartMode.detached` reached the server about 2 s after its starter had ended.
- **On the owner's Windows, no firewall question and no console window appeared** (the owner watched the screen). Dart starts a detached process on Windows with `DETACHED_PROCESS` (the SDK's `runtime/bin/process_win.cc`); the child's stdout and stderr were pipes, not a console.

**2026-10-17, built and reviewed.** Built by a helper (Opus medium) in its own worktree, reviewed on two axes (standards: Sonnet high; spec: Opus high), two fix rounds, each checked (Opus high), then one change of mine.

- **How it works.** `appstein analysis-host <project>` (hidden) runs `runAnalysisHost`: the guard and the analysis server as in 1d.2, a listener on `127.0.0.1`, and the address file. The client, `analysisHostCodeAnalysis`, is one more implementation of the code analysis interface; the `verify` tool of `appstein mcp` uses it (`hostCodeAnalysis`). The answer types moved into `appstein_protocol` (`code_reading.dart`) so there is one data format; the messages are one JSON object per line (`analysis_host_messages.dart`). `APPSTEIN_ANALYSIS_HOST_FOLDER` overrides the address-file folder, for tests.
- **Fix round 1:** the idle stop counted from "no client connected", so a stuck client kept the host and its server for ever, now from the last question, and a connection that asks nothing that long is closed; a client held the server for its whole tool call (`flutter test` included), now each question takes the server alone, answered in arrival order across connections; the client trusted any address file, now off Windows it refuses a folder or file that is not the user's own with modes 700 and 600; a host that can't start leaves its reason in `host-<hash>.failed`; tests for paths with spaces and letter case, the file modes, and the whole set of `dart.*` findings equal to a terminal run's; one `chmod` helper, one OS check, names.
- **Fix round 2:** the client's time limit counted the wait in the host's queue, and the host still ran a question whose client had given up, so `--apply` could write after its client reported failure; now the host sends a turn line when a question begins, the client's limit starts there, a queued question whose client left is never begun, and a rewrite checks its client again before its first write. The host refuses a link as its folder.
- **Decided by Claude, not asked of the owner:** off Windows with no `XDG_RUNTIME_DIR`, the folder is `<temp>/appstein-<uid>`, so another user can't even make it first; each question takes the server alone, so between two questions of one run another session's reading may land (no edit is lost: every write still needs the file to hold the text it was planned from; at worst a `dart fix` hint is wrong until ticket 03); the wait for a turn has a safety limit of 15 minutes (`analysisHostTurnLimit`, my change after round 2), so a host stuck before it begins a question can't hold a tool call or a hook for ever; a host start limit of 60 s; answer limits of the question's own plus 30 s.
- **Left for ticket 03:** racing starters, a host of another version, an SDK change, a stale address file (now simply overwritten by the next host), strict ordering of one client's questions.
- **Not verified:** Linux and macOS (the mode and link tests are skipped on Windows; CI will run them); the compiled binary's host on screen (tests run from source).
- **Full gate in the slice branch:** `tool/test_all.dart` passed: protocol 82, engine 1908 twice (10 skipped), CLI 207, lints 19, repo tools 378 (1 skipped); format, analyze, gen_docs and the guide check clean; no Dart process left afterwards.
