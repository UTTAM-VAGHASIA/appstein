# Measure the hook against 5 s

**What to build:** the proof of design §15's 5 s target where an agent meets it: `tool/measure_sync.dart` times the compiled `appstein verify --fast --hook claude` from its process start to its exit, with the project's analysis host ready, on Linux, macOS and Windows in CI. It also records the hook with no host running, and checks that sessions share one analysis server (spec: "Measuring").

**Blocked by:** 04, 06, 09.

Status: resolved

- [x] **The hook row:** on the 200-file app with a ready host, edit one file to add an error, then run the compiled hook with Claude Code's input on stdin, timed from process start until it has exited and its output has closed (the owner, 2026-10-21). Each of the three runs follows its own edit (or uses its own session ID), so ticket 06's "nothing changed" rule never makes a run silent. The median of three must be under 5 s (5.000 s or more fails), and every run must exit 2 and name the error.
- [x] **The cold row:** the same hook with no host running (it starts one and waits) and a warm analysis cache, labelled so (the owner, 2026-10-21), recorded with no limit other than the cap; whether it reached the cap is printed.
- [x] **The sharing check:** two `appstein mcp` processes and a hook on one project leave exactly one analysis server running, or the tool fails; the memory of two sessions is recorded beside that of one.
- [x] The 1d.2 rows still pass: the `verify` tool (now through the host) and the terminal runs.
- [x] The tool's own logic is tested as 1d.2's measurement tool is (scripted processes).
- [x] The owner is asked before CI is run for the numbers. If the hook row misses 5 s anywhere, stop and ask the owner; never change the limit. The fallback considered is the host running the whole `verify` (decision record 0002).

## Comments

**2026-10-21, built and reviewed; CI not run yet.** Built by a helper (Sonnet high) in its own worktree, reviewed on two axes (standards: Sonnet high; spec: Opus high), two fix rounds (the same helper), each checked (Opus high). Boxes 6 and 7 wait for the CI run, which the owner is asked for first.

- **How it works.** `tool/measure_sync.dart` keeps its rows and gains the hook's (`tool/src/hook_rows.dart`, `hook_process.dart`, `hook_measurement.dart`, `sharing_check.dart`, `analysis_hosts.dart`, with the run's settings in `MeasureContext`). Every process it starts gets a private analysis-host folder, so a developer's own hosts are never touched, and the tool ends the hosts it started, also when it fails. The no-host row runs first; then clean hooks with fresh session IDs until one is not cut; then the three timed hooks, each after its own edit and with its own session ID (ticket 06's silence never applies); then the sharing check.
- **Decided by the owner (2026-10-21):** the hook is timed from just before its process starts until it has exited and its stdout and stderr have both closed, whichever is later, since that is what Claude Code waits for. The no-host row uses a warm analysis cache (a new session, or after a host's idle stop) and says so in its label. Both written into the spec, this ticket and design §15.
- **Decided by Claude:** the terminal fast row keeps the default 20 s cap, the cap a user gets; a run the cap cut fails the row with a message naming the cap, and the time is still printed. The sharing check counts analysis servers by where they sit (Dart programs started since the check began, in the tree of the host, a session or an orphan, a root's Dart child counting once), not by any program's name, and counts a second orphaned host too: the spec says exactly one server, failing otherwise, so a false failure is the safe direction. A host's process is ended only while it is still the host (its start no later than its address file, within 2 s).
- **Review rounds fixed:** a server found by its parent's name, which only Windows gives (the Linux binary may be named `dart:…`), and then a rule that would count 0 when the host and its guard are both named so; a hook run with no time bound (now 120 s, then killed); untestable logic in `main` moved into tested files; a global; duplicated run records, wait loops, path helpers and test helpers; a process ID killed without checking it was the host; errors other than the tool's own escaping without tables.
- **Proof the tests bite:** the builder wrote the new tests first and showed them red; Claude broke the root rule (two of four namings counted 0 servers) and the kill check (a reused process ID was killed) in the slice branch, saw both red, and restored them byte for byte.
- **Local run (Windows, one run, not CI's numbers):** hook with the host ready 1,977 ms median (1,977, 2,028, 1,960), every run exit 2 naming the error; no host, warm cache 6,075 ms, not cut; 1 host and 1 server after two sessions and a hook; memory 0.93 GB for one session, 1.00 GB for two; terminal fast cold 11.4 s, under the cap.
- **Known limits (in the CI guide):** a server under a process that is none of host, session or orphan is not seen; a Linux subreaper hides orphans; on Linux and macOS a dead host's guard is adopted by process 1, so the clean-up's tree search cannot find it; an error thrown while hosts are being ended ends the run without its tables; a process ID reused within 2 s of the address file could be taken for the host.
- **Carried from ticket 09:** a cold terminal fast run on a slow CI runner over 20 s now fails the terminal row (exit 3) instead of recording a time. Locally it took 11.4 s.
- **Not verified:** Linux and macOS process naming and listing for the compiled binary, and the pipe-open check there: CI is their first run. The Windows-skipped tests (ticket 04's untrusted folder, tickets 02/03's mode and link tests) run in CI's Linux and macOS `test` job (`.github/workflows/ci.yml`, the plain `dart test` of every package); their results are read when CI runs.

**2026-10-21, the first CI run (39551693885) and what it found.** All three `measure` jobs passed: the hook with a host ready took a median of 1,453 ms on Linux, 1,869 ms on Windows and 1,393 ms on macOS, every run exit 2 naming the error. But the `test` jobs failed on Linux and macOS, and that run's numbers are not the ones written into the spec (box 7 asks for a fully green run).

- **A real Linux and macOS bug, from tickets 02 and 03.** The host made its folder (mode 755) and then set it to 700 with a separate `chmod`; a client that looked in between refused the folder for good ("has mode 755, not 700"). Four tests failed on it; one more test (a host that fails before it has an address) could never pass off Windows. Fixed as the owner chose: a client checks the folder's mode once there is an address file, and again in full after every read, and uses an address only when a second read gives the same one; a folder others can write to is always refused; the reason a host leaves is read only from a folder that passes the check. The broken test was split into a host-side and a client-side test. A copy with the old rule put back (CI run 39564998975) failed the new tests on Linux as predicted.
- **Test-only faults the first full Linux run exposed:** sockets that tests open now ignore a peer's reset (EPIPE on Linux, ECONNRESET on macOS); one test takes a reset as a close; one waits for the stop request instead of a fixed 500 ms; the lock test allows whole-second modified times (Dart below 3.13 on Linux, the `min-sdk` job). The host now ends at once when its port fails (the owner).
- **CI:** the `test` and `min-sdk` jobs got a 60-minute limit, after the Windows `test` job's runner stopped answering at 59 minutes (its rerun passed in 34).
- **Two new tickets:** 12 (on Linux with no `XDG_RUNTIME_DIR`, another user can make `/tmp/appstein-<uid>` first; the guide's claim that they can't was false), and 13 (a test file that reports an error after it loaded was called unloadable).
