# The cap, and hooks through the host

**What to build:** `verify.fast_timeout_seconds` becomes a real cap on every fast run, and the hooks ask the project's analysis host. A fast hook run that finds no host starts one and waits for it up to the cap; when the cap comes first, its code checks are named as not run and the agent is told its edit's code checks are pending. A full hook run starts a host when none runs and waits for it without the cap (spec: "The cap", "Who starts it").

**Blocked by:** 03, 05.

Status: resolved

- [x] Every fast run (hook, `verify` tool, terminal) is capped by `verify.fast_timeout_seconds` (default 20 s), counted from the run's start; waiting for a host or a server to start counts.
- [x] At the cap, the checks that hadn't finished are named among the checks not run with the reason (for example "the analysis server is starting"), the run is partial, and no file leaves the unverified files. The next run asks again. Tested with a scripted slow code analysis and a short cap.
- [x] A fast hook run asks the project's host; with none answering, it starts one as a detached process (the same start as ticket 02's) and waits up to the cap.
- [x] When the cap comes first: exit 0, or 2 when other checks found errors; the agent's context says the edit's code checks are pending because the analysis server is starting.
- [x] The host a hook started keeps running after the hook ends, and the next hook gets warm answers from it.
- [x] A full hook run starts a host when none runs and waits for it, limited only by the server's start limit.
- [x] Full runs have no cap.
- [x] The guide pages for the configuration and the verifier say what the cap does (the page that says the key is read by no command yet is corrected); the guide check passes.

## Comments

**2026-10-19/20, built and reviewed.** Built by a helper (Sonnet high) in its own worktree, reviewed on two axes (standards: Sonnet high; spec: Opus high), two fix rounds (the same helper), each checked (Opus high); one doc sentence fixed by Claude after the last check.

- **How it works.** One `RunClock` per run, made when the CLI command starts or when the `verify` tool call arrives, carries the cap (`verify.fast_timeout_seconds`, default 20 s; none for a full run). The cap races each question to the code analysis (`VerifyGathering._ask`): a question cut at the cap names its check, and every later check that needs the analysis, among the checks not run with a "still pending" reason that states the real time; the run is partial, so no file leaves the unverified files and the next run asks again. A late answer is dropped. Hook runs now ask the project's host (`startHost: true`, fast and full); a terminal run still never starts one. A full (Stop) run is never cut and waits for the host as long as its start limit allows.
- **Decided by the owner (2026-10-19):** the `verify` tool's wait for its turn counts toward the cap (the clock starts when the call arrives); the cap cuts only the wait for the code analysis, while the refresh and the knowledge-lock save count but are never cut, since cutting either would leave the store half-written.
- **Decided by the owner (2026-10-20), after the desk's watcher caught Claude documenting an overrun instead of fixing it:** a fast hook ends within its cap, also when its time is spent before its first question. A hook run (fast or full) looks for the project's host and requests its launch at the very start of the run, in parallel with the refresh, and the first question joins that same look, so one host is launched and nothing is left to wait for at the cap; the `verify` tool does the same when a call arrives. A terminal run still starts nothing. This replaced a wait at the end of the run (3 s, then 0.5 s) that let a hook end past its cap.
- **Decided by the owner (2026-10-20), after the desk's watcher saw a cut run exit 0 on code with a compile error:** a run cut by the cap never reads as a pass. A terminal fast run with a check cut by the cap exits 3, "Appstein could not finish checking", with the pending checks and any errors the other checks found (3 wins over 1); checks not run for any other reason keep 1d.1's rule. The JSON result (terminal `--format json` and the `verify` tool's `structuredContent`, one object) carries `incomplete: true` and `incompleteReason`, absent when nothing was cut. Hooks keep their answer: exit 0, or 2 with errors, and the agent is told its code checks are pending. Written into the design (§9.1, §9.5, the JSON output) and the slice spec.
- **Decided by Claude, implementing those:** a fast tool call past its cap never waits for another call's run (`_calls`), only for the refresh, which now has its own in-process turn so two refreshes never overlap; a cut during the `dart fix` questions loses only the fix hints, not the check. After the launch-at-start check: a look for the host that failed stays the run's answer, so a run never launches two hosts; the connect, the poll and the address-lock wait are cancelled when the run's client closes, so nothing of the look keeps a hook's process alive; the client looks up the host's process before dialing, since a refused loopback connect takes about 2 s on Windows (measured 2045 ms), and Windows' refused code 1225 is now known as refused.
