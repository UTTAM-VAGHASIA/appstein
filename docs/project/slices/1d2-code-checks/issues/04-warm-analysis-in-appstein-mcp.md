# Warm analysis in `appstein mcp`

**What to build:** the `verify` MCP tool answers from warm analysis. `appstein mcp` starts the project's analysis server when a `verify` call first needs it, keeps it running between calls, stops it when it has been idle for 10 minutes, and stops it when it stops itself. An agent that edits a file and calls `verify` gets the new findings without the server being started again, and a session that never verifies holds no analysis server (decision record 0001, "Memory").

**Blocked by:** 03.

Status: resolved

- [x] Starting `appstein mcp` starts no analysis server. The first `verify` call starts one for the project, waits for it and then answers.
- [x] An analysis server that no `verify` call has used for 10 minutes is stopped, with its guard. The next `verify` call starts it again and answers correctly. The time is one named constant, and a test can shorten it.
- [x] A `verify` call that arrives while the server is starting, or while another call is being answered, waits and then answers; two calls never start two servers.
- [x] Two `verify` calls with an edit between them use the same analysis server, and the second reports the change: an error added on disk between the calls appears, and an error removed is gone.
- [x] A reading is never older than the files on disk. The review of ticket 03 saw a kept server answer from before an edit when asked at once (the error appeared 50 ms later; a deleted file's findings stayed for 2 s). The barrier must not be a wait: the reading is taken only after the server has been made to take in every change the knowledge refresh saw, and has said its analysis is done again. Tested with an edit, a new file and a deleted file, each followed at once by a call, many times in a row.
- [x] A reading is never taken from a server that has died. Each reading follows a request the server answered in that call, so a server that died since the last call is found out by the reading, not by the one after it (see the comment on ticket 03 about a test that failed once).
- [x] A plugin failure is reported only while it holds. On a kept server, a `dart.plugin_failed` finding whose cause was removed from `analysis_options.yaml` is gone in the next call, without restarting `appstein mcp`.
- [x] The idle stop never fires while a call is being answered or while the server is starting.
- [x] The findings of the tool equal the findings of a terminal run on the same project state.
- [x] When `appstein mcp` stops (its input closes, or it is killed), the analysis server stops too. Checked on Windows.
- [x] An analysis server that died is started again by the next `verify` call. When it can't be started, the tool's reply is an error with the reason and "run `appstein doctor`", and the MCP server keeps running.
- [x] Appstein never ends a process it can't prove is its own. `AnalysisServer` (ticket 03, already pushed) ends a server by its process ID alone in two places: after a guard that ended without saying so, and as the last step of a stop. Windows gives an ended process's ID to a new program within seconds, so such a kill could close an unrelated program. Before any kill by ID, the process is shown to be the one Appstein started (for example by its start time, taken when it was started, and its image), and when that can't be shown, nothing is killed and the leftover is reported. Tested with an ID that has ended and with an ID that belongs to another process. Added 2026-10-14, found by this ticket's builder. The owner's decisions the same day: when it can't be shown, the `verify` output says so with the process ID and the command to end it, and Appstein checks again at the next `verify` call; Appstein asks the operating system for the start time and program once after each server start, in the background, and once before any kill by ID (about 0.3 to 0.5 s on Windows, off the path of a `verify` call), unless the review finds a cheaper reliable way.
- [x] The other tools are unaffected: none of them waits for the analysis server.
- [x] The guide pages for the MCP server and the verifier say how warm analysis works; the guide check passes.

## Comments

**2026-10-14, what was established by running the real server** (Windows development machine, the pinned SDK; the scripts were throwaway and are not in the repo).

- **The barrier.** Before each reading, Appstein looks at the project's files itself (each Dart file's time and size; the text of `analysis_options.yaml`, `pubspec.yaml` and `.dart_tool/package_config.json`), tells the server each Dart file that changed, appeared or is gone with `analysis.updateContent` and the change `remove`, asks `analysis.getErrors` for one of those files, and waits for the server's "done". With nothing done, 61 of 120 readings taken at once after a change were old; with this, 0 of 120, and 0 of 100 in the engine's test on the fixture app in every run. With the `appstein_lints` plugin on, 0 of 50 (by hand, not a test).
- **It differs from this ticket's wording in one thing:** the changes are found by the analysis's own look at the disk, not taken from the knowledge refresh. The refresh doesn't see every Dart file the server covers yet (ticket 06 widens it), and there is none to take from when it failed.
- **What it costs per call:** about 40 to 50 ms with nothing changed, 45 to 113 ms at the median after a change (0.35 s at most), on the fixture app. Not measured on the 200-file app: the look reads every folder that doesn't start with a dot, so ticket 11 must measure it there.
- **What was tried and is not used.** `analysis.reanalyze` is answered at once and the rebuild starts about 0.2 s later, with nothing to tell the two apart, so it is no barrier. Sending `analysis.setAnalysisRoots` again was not tried.
- **The plugin-failure rule.** The server tells a plugin it can't load once per rebuild and says nothing when the cause is removed. So when a file that sets how the project is analyzed has changed, the server is started again, and the new one tells the failure only if it still holds. That costs one start for that call (about 2 s on the fixture app; 7 to 20 s on the 200-file app by the decision record's numbers), also after a `pubspec.yaml` edit or a `flutter pub get`. It is tested on the reading (`pluginFailures`), not through the tool's `dart.plugin_failed` finding.
- **The dead-server rule.** Every reading follows a request answered during that reading. A server that had answered before and is found dead is replaced, and the new one answers the same call; a second failure is an error.
- **A fault found in the guard of ticket 03, and fixed.** A guard that had passed a request on to a server that had just been killed said `guard ended`, returned, and its process never ended, so the reading waited 180 s. Seen in about 1 run in 5 of the test that kills the server and asks at once (5 of about 25 runs). The guard now ends its process with `exit`. After that: 54 of 55 runs passed.
- **One failure is not explained.** The one run of those 55 failed within a second with "its guard ended without it, with exit code -1", and did not come back in 35 traced runs. Not waited away or retried.
- **Process IDs in tests.** Windows gives an ended process's ID to a new one within seconds. The tests' helpers now know a process by its ID and its start, and no test compares IDs to tell a new server from an old one. This may be what failed "a server that dies" after ticket 03 (`goneWithin` saw an ID alive), but that is not proven: the guard that stays would give the same failure.
- **The plugin-failure line and the dead-server line are ticked with the limits said above:** the plugin failure is tested on the reading (the review ran it through the tool), and one run in 55 failed in a way that was not explained then (see below).

**2026-10-14, after the review (fix round 1).** What changed, and what was established by running the real server again.

- **The look now covers what the analysis reads outside the project folder.** The review showed a kept server never saw a change in a path dependency's source or in an `analysis_options.yaml` above the project. The look (`DiskLook`) now holds the source of every package the package configuration places at a relative location, the nearest options file above a project that has none, every file the options files include (by a path or from a package, followed once each), and the package configuration the project uses, its own or the nearest above. A package's file outside the root is taken in when told with `analysis.updateContent` (12 of 12; untold it was not seen after 3 s). The settings restart the server.
- **`pubspec.yaml` keeps the restart, on evidence.** The lint `depend_on_referenced_packages` reads the dependencies from its text. With the server told `pubspec.yaml` and the Dart file, the reading taken at once was old in 4 of 4 tries and right 3 s later.
- **A stop no longer waits for the server to end by itself.** It asks, waits a quarter of a second for the answer, and closes the guard's input. `dart analyze` ends its server the same way (the request, then a kill). On the 200-file app a stop went from 4.1 to 4.2 s down to 0.28 to 0.29 s, a reading after a settings change from 13.6 to 17 s down to 8.8 s, and the starts after six such stops took as long as before.
- **The look no longer blocks the event loop.** On the 200-file app: a reading with nothing changed 51 ms at the median, 79 ms with a `build/` of 6,000 files and 173 ms with 26,000; the event loop stood still for at most 33, 37 and 61 ms (100 to 146 ms and about 0.5 s before). A folder the options exclude is still walked: an excluded file that is imported is still read by the analyzer.
- **Kills by process ID are checked** (`process_identity.dart`): a process is its ID, its start and its program, asked of `kernel32` through `dart:ffi` on Windows and of `ps` elsewhere, recorded when the guard names its processes and looked up again before a kill. What can't be shown is left, told in `VerifyResult.notices` with the command to end it by hand, and looked at again at every reading. `notices` is a new field of the result's JSON, present only when there is something to tell.
- **The failure "its guard ended without it, with exit code -1":** that message is what a killed guard gives, and the two kills by ID were the only places that could kill a process Appstein did not hold. With the identity checked, a reused ID has another start and is not killed, so that cause is closed. It was not reproduced, so it is not proven that it was the cause.
- **Not covered after round 1, and written in the guide:** a path dependency named by an absolute path (closed in round 2); a Dart file outside the project that no local package holds; a same-size edit whose file time was put back more than 2 s after the last look (accepted by the owner); `AndroidManifest.xml` and `lib/fix_data.yaml`; a real pub workspace was not tried with `pub` (the re-review did: 0 old); a reading while a real `pub get` runs was not tried.

**2026-10-14, after the re-review (fix round 2).**

- **A path dependency at an absolute location is followed.** The look now walks every package the package configuration places outside pub's cache and the SDK, whatever the form of its location (`unchangingFolders`: `PUB_CACHE`, else `%LOCALAPPDATA%\Pub\Cache` and `%APPDATA%\Pub\Cache` on Windows, `~/.pub-cache` elsewhere, and the SDK that runs the server with the Flutter SDK around it). Real server, absolute `file:` location, 10 rounds read at once: 0 old. With such a package left out on purpose, the same test failed at round 0.
- **The 2 s rule has a test of its own** on the look, with no server. With the rule taken out, it fails ("Actual: []"); with it, it passes. The server test can't show the rule, because the server's watcher usually wins.
- **A left process is reported once** (one entry per process ID), also when a guard that ignores its input closing makes the stop and the orphan rule both weigh it.
- **"Can't tell" is reported, never dropped.** The identity lookup answers running, gone or unknown; unknown (a failed question, or a `ps` without `lstart`, where `/proc` still shows the process) is a left process with the command `taskkill -PID <ID> -F` or `kill <ID>`.
- **A stop no longer sends `server.shutdown`.** The re-review saw no answer within 250 ms in 60 of 60 stops, so every stop ended with the guard's kill anyway.
- **The command to end a process by hand** uses `-` switches (`taskkill -PID 4711 -FI "IMAGENAME eq dart.exe" -F`), which worked as typed in cmd, PowerShell and Git Bash on the development machine.
- **Two timing-sensitive tests made deterministic or explained:** the scripted server of the close test now never finishes on its own; the CLI test "when its input closes" now names what outlived `appstein mcp` (program, start, command line, parent), and was run under load to find it (see the report of this round).
- **The CLI's helpers start no process to ask about one** on Windows (`kernel32`) and Linux (`/proc`); macOS runs `ps`, which `childProcesses` leaves out by name.
