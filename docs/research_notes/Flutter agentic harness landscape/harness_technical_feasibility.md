# Technical Feasibility and Risks of a Flutter-Desktop Multi-Agent Harness Wrapping Agent CLIs (as of 2026-09-28)

Scope note: research done on 2026-09-28. Every item carries a URL or is labelled as an inference. The legal and ToS picture changed several times in 2026 (Feb, Apr, May, Jun), so re-check the Anthropic and Google items before shipping. Correction to the brief: brainless.swerdlow.dev is not a wrapper or harness. It is a shadcn/ui component registry of React components (headers, messages, thinking, tool calls, diffs, session blocks) that recreate Claude Code, Codex, and Grok interfaces. It is a design reference for "native UI instead of a `<pre>` terminal dump," and it does not handle any process control or auth — [brainless](https://brainless.swerdlow.dev/).

## (a) Programmatic control interfaces per agent CLI, and whether ACP works as a universal abstraction

### Takeaway
All four target agents expose structured, machine-readable control surfaces: Claude Code `-p` stream-json and the Agent SDK, Codex `exec --json` and `app-server` JSON-RPC, Gemini CLI headless stream-json, and OpenCode's HTTP/OpenAPI server with SSE. That makes native-UI rendering feasible without scraping a PTY. ACP now covers about 40 agents, natively or through adapters (Claude and Codex go through adapters), and it has Dart SDKs. It is a strong candidate for a common abstraction layer, with per-CLI native adapters kept for features ACP does not expose.

### Cited Findings
**Claude Code (Anthropic)**
- `claude -p` / `--print` runs non-interactively. `--output-format` takes `text`, `json` (result, session ID, metadata, `total_cost_usd`), or `stream-json` (NDJSON). Token streaming needs `--output-format stream-json --verbose --include-partial-messages`. The last line is a `result` message — [Claude Code headless docs](https://code.claude.com/docs/en/headless)
- `--json-schema` gives schema-conforming output in `structured_output`. `--continue` and `--resume <session_id>` continue sessions, and `--resume` also accepts a transcript `.jsonl` path — [headless docs](https://code.claude.com/docs/en/headless)
- The stream carries a `system/init` event (model, tools, `mcp_servers`, `mcp_server_errors`, `plugins`, `plugin_errors`, and a `capabilities` array for feature detection from v2.1.205), `system/api_retry` events (with error categories such as `rate_limit`, `authentication_failed`, `billing_error`), and `permission_denied` system messages. Subagent messages carry a `parent_tool_use_id`, so the nesting tree can be rebuilt. `--forward-subagent-text` forwards subagent text/thinking (v2.1.211+) — [headless docs](https://code.claude.com/docs/en/headless)
- Permission control: `--allowedTools` (rule syntax such as `Bash(git diff *)`), `--permission-mode` (`auto`, `dontAsk`, `acceptEdits`; the default for `-p` is Manual), `--permission-prompts none` for unattended runs (v2.1.259+), and `--permission-prompt-tool` to delegate approvals to an MCP tool. SDK apps get a `canUseTool` callback — [headless docs](https://code.claude.com/docs/en/headless)
- `--bare` skips auto-discovery of hooks, skills, plugins, MCP servers, and CLAUDE.md, and does not read OAuth credentials or the keychain. It needs `ANTHROPIC_API_KEY` or `apiKeyHelper`. Anthropic says `--bare` "will become the default for `-p` in a future release." This matters for a subscription-based harness, because bare mode does not use the subscription login — [headless docs](https://code.claude.com/docs/en/headless)
- Without `--bare`, a `-p` session runs the project's `.claude/settings.json` hooks and `.mcp.json` servers "even in a folder you've never trusted," with no trust dialog. This is a security consideration for a harness that opens arbitrary repos — [headless docs](https://code.claude.com/docs/en/headless)
- SIGTERM exits with code 143 and leaves the turn unfinished. SIGINT or the SDK's `interrupt()` ends the turn cleanly — [headless docs](https://code.claude.com/docs/en/headless)
- Agent SDK: Python and TypeScript only. It is "a library that runs the Claude Code binary." It supports hooks, subagents, MCP, permissions, sessions (resume/fork), skills, and plugins. For other languages the docs say to "run the CLI as a subprocess with the `-p` flag and `--output-format json`" — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)
- The Agent SDK is governed by Anthropic's Commercial Terms. Branding rule: products may not call themselves "Claude Code" or mimic Claude Code ASCII art or visuals. "Claude Agent" or "{YourAgentName} Powered by Claude" is allowed — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)

**OpenAI Codex CLI**
- `codex exec --json` emits JSONL thread events (`thread.started`, `turn.started`, `turn.completed`/`turn.failed`, `item.*`, `error`) — [takopi Codex exec JSON cheatsheet](https://takopi.dev/reference/runners/codex/exec-json-cheatsheet/) (secondary). The TypeScript SDK (`@openai/codex-sdk`) "spawns the CLI and exchanges JSONL events over stdin/stdout" and offers `runStreamed()` — [openai/codex sdk/typescript](https://github.com/openai/codex/tree/main/sdk/typescript)
- `codex app-server`: JSON-RPC 2.0 "to power rich clients" such as the VS Code extension. It covers auth, conversation history, approvals, and streamed events. Transports: stdio NDJSON (default), WebSocket (experimental), and Unix socket. Methods include `initialize`, `thread/start`, `thread/resume`, `turn/start`, `turn/steer`, approval requests for commands and file changes, `item/started`/`item/completed`, and message/reasoning deltas. Some APIs (`process/*`, paginated history, WebSocket) are "experimental and unsupported for production." OpenAI recommends the Codex SDK instead for automation/CI — [Codex app-server docs](https://learn.chatgpt.com/docs/app-server) (redirected from developers.openai.com/codex/app-server)
- OpenClaw runs OpenAI turns "through the native Codex app-server runtime by default" with Codex/ChatGPT sign-in. This shows a third party building on app-server in production — [OpenClaw Codex harness docs](https://docs.openclaw.ai/plugins/codex-harness)
- Codex auth: ChatGPT sign-in or API key. Credentials are cached in `~/.codex/auth.json`, the OS keyring, or in memory. Device-code login is in beta. For CI the docs recommend API keys or enterprise access tokens — [Codex auth docs](https://learn.chatgpt.com/docs/auth)

**Gemini CLI**
- Headless mode starts with `-p/--prompt` or in a non-TTY. `--output-format json` returns `response`, `stats`, `error`. `stream-json` emits JSONL events `init`, `message`, `tool_use`, `tool_result`, `error`, `result`. Exit codes: 0, 1, 42 (input error), 53 (turn limit) — [Gemini CLI headless docs](https://geminicli.com/docs/cli/headless/)
- Gemini CLI is Zed's reference ACP implementation — [Zed external agents](https://zed.dev/docs/ai/external-agents)

**OpenCode**
- `opencode serve` is a headless HTTP server on `127.0.0.1:4096` by default. It publishes an OpenAPI 3.1 spec at `/doc`, supports optional basic auth via `OPENCODE_SERVER_PASSWORD`, and provides endpoints for sessions, messages, permissions, files, providers/models, `/tui` control, and SSE events. A generated SDK is available — [OpenCode server docs](https://opencode.ai/docs/server/)

**ACP (Agent Client Protocol)**
- The ACP agents list shows native support in Gemini CLI, GitHub Copilot (public preview as of Jan 2026), OpenCode, Cursor, Cline, Goose, Junie, Kiro CLI, Qwen Code, OpenHands, Factory Droid, Mistral Vibe, OpenClaw, and others. **Claude Agent**, **Codex CLI**, and **Pi** are supported only through adapters — [agentclientprotocol.com agents](https://agentclientprotocol.com/get-started/agents)
- Zed runs Gemini CLI, Claude Agent, and Codex as external agents over ACP — [Zed external agents](https://zed.dev/docs/ai/external-agents). Other ACP clients: marimo ([marimo docs](https://docs.marimo.io/guides/editor_features/agents/)), a cross-platform acp-ui client ([formulahendry/acp-ui](https://github.com/formulahendry/acp-ui)), and an AI SDK community provider ([ai-sdk.dev ACP](https://ai-sdk.dev/providers/community-providers/acp))
- Dart ACP SDKs exist on pub.dev: `acp_dart` ([pub.dev](https://pub.dev/packages/acp_dart)) and `dart_acp` (library plus CLI) ([pub.dev docs](https://pub.dev/documentation/dart_acp/latest/)). One repo describes itself as the "Official Dart SDK for ACP," and a PR ports it to the TypeScript SDK v1.5 protocol surface — [SkrOYC/acp-dart](https://github.com/SkrOYC/acp-dart), [PR #22](https://github.com/SkrOYC/acp-dart/pull/22). There are competing Dart packages, so check which one is maintained.

### Inferences
- A "universal" layer is realistic along two paths. (1) ACP as the default transport covers Gemini, OpenCode, Copilot, Cursor, and many long-tail agents with one client implementation. (2) Native adapters for the "big two" (Claude Code stream-json/Agent SDK, Codex app-server) get richer events: cost, `parent_tool_use_id` subagent trees, `turn/steer`, diffs, retries, and plugin/MCP health. The Claude and Codex ACP adapters are third-party (Zed) and lag or flatten features, so a harness that relies only on ACP would give up fidelity for its two most important agents.
- The event models map well to native widgets. Every CLI exposes message deltas, tool_use/tool_result or item lifecycle events, approvals, and a final result with usage. That is enough for Brainless-style components (message, thinking, tool-call card, diff viewer, approval dialog) without a terminal emulator. A raw PTY view would stay useful as a fallback or debug pane.
- Claude Code changes quickly: the docs cite behaviour changes up to v2.1.283. Adapters should feature-detect through `system/init.capabilities`, not pin version strings.
- The repo-trust issue (hooks and MCP from `.claude/` run without a trust prompt under `-p`) means the harness should run its own trust prompt before launching agents in a new repo, or use `--bare` / `--setting-sources`.

### Gaps
- I did not verify Codex CLI's own MCP-server mode (`codex mcp-server`) or the current Codex Python SDK status from primary docs. One secondary source says Python uses `codex exec --json` as a subprocess ([hexdocs codex_sdk architecture](https://hexdocs.pm/codex_sdk/02-architecture.html)).
- I did not confirm Gemini CLI's exact ACP flag name (`--experimental-acp` vs `--acp`) or `--approval-mode` values. The fetched headless page did not document them.
- I found no primary source for the ACP spec version or the list of optional capabilities (e.g., terminals, plans, diffs) in Sept 2026.
- Given the Gemini consumer deprecation (section b), Antigravity CLI's programmatic interface is now relevant and I did not research it.

## (b) Terms of service / licensing risks of wrapping consumer subscriptions (Anthropic, OpenAI, Google)

### Takeaway
The legally safest design is: spawn the **unmodified official CLI binary**, have the user sign in **through the vendor's own login flow**, and never read, store, proxy, or re-use OAuth tokens. Under that design, Anthropic's current docs explicitly allow subscription sign-in. OpenAI is permissive in practice. Google consumer subscriptions (AI Pro/Ultra) no longer work with Gemini CLI at all as of June 18, 2026. Token-harvesting or proxying approaches (the OpenClaw pattern) have caused account bans from Google and blocking from Anthropic. Uncertainty is high: Anthropic changed course four times in 2026 and "reserves the right to take measures ... without prior notice."

### Cited Findings
**Anthropic: timeline**
- Enforcement blocking third-party use of Max subscriptions began in January 2026. On **Feb 19, 2026** Anthropic updated its docs to say OAuth tokens from Free/Pro/Max are for Claude Code and Claude.ai only, and that use "with any other products, tools, or services, including the Agent SDK, is unauthorized" — [WinBuzzer](https://winbuzzer.com/2026/02/19/anthropic-bans-claude-subscription-oauth-in-third-party-apps-xcxwbn/), [GIGAZINE](https://gigazine.net/gsc_news/en/20260220-anthropic-third-party-block/) (secondary reports of the doc change)
- **Apr 3–4, 2026**: announcement, with enforcement from Apr 4 12pm PT, that Pro/Max subscriptions can no longer power third-party agentic tools like OpenClaw. Boris Cherny (Head of Claude Code): "our subscriptions weren't built for the usage patterns of these third-party tools". He cited prompt-cache inefficiency. API keys and "Extra Usage" pay-as-you-go stayed available — [VentureBeat](https://venturebeat.com/technology/anthropic-cuts-off-the-ability-to-use-claude-subscriptions-with-openclaw-and), [TechCrunch](https://techcrunch.com/2026/04/04/anthropic-says-claude-code-subscribers-will-need-to-pay-extra-for-openclaw-support/)
- **May 13, 2026**: Anthropic reinstated third-party agent usage (OpenClaw, Conductor, Zed, Jean named) with a planned monthly "Agent SDK credit": Pro $20, Max 5x $100, Max 20x $200, Team Premium $100/seat, Enterprise Premium $200/seat. `claude -p`, GitHub Actions, and third-party tools would draw from it instead of normal limits. It was "explicitly allowing third-party apps like Conductor and OpenClaw to authenticate via the Agent SDK" — [VentureBeat](https://venturebeat.com/technology/anthropic-reinstates-openclaw-and-third-party-agent-usage-on-claude-subscriptions-with-a-catch). Zed's analysis estimated this would remove a "roughly 15-30x" subscription subsidy for agent use — [Zed blog, May 14 2026](https://zed.dev/blog/anthropic-subscription-changes)
- **June 15, 2026**: the credit change was **paused**. "For now, nothing has changed: Claude Agent SDK, `claude -p`, and third-party app usage still draw from your subscription's usage limits." The planned credit explicitly covered "Third-party apps that authenticate with your Claude subscription through the Agent SDK" — [Claude Help Center](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan). Zed's June 16 update says Anthropic will give "advance notice before any future change" — [Zed blog](https://zed.dev/blog/anthropic-subscription-changes)

**Anthropic: current doc language (fetched 2026-09-28)**
- "OAuth authentication is intended exclusively for purchasers of Claude Free, Pro, Max, Team, and Enterprise ... to support ordinary use of Claude Code and other native Anthropic applications." Developers building products, "including those using the Agent SDK, should use API key authentication." "Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, or Max plan credentials on behalf of their users ... developers may not collect, store, or intermediate Claude.ai credentials or session tokens — sign-in to a Claude account must complete through Anthropic's own flow." — [Claude Code Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)
- The same page carves out: "Nor does it prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code." Products that run Claude Code must not modify the binary, must not "remove, disable, or restrict any authentication method built into it," and must not "pay for, resell, or intermediate Claude usage." Each end user must authenticate with their own key or subscription. They may say the product "runs Claude Code" but may not use the name or logo in their product name — [Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)
- "Advertised usage limits for Pro and Max plans assume ordinary, individual usage of Claude Code and the Agent SDK." "Anthropic reserves the right to take measures to enforce these restrictions and may do so without prior notice." — [Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)
- The Agent SDK overview still says: "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK." — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview). **Conflict:** this conflicts with the Help Center article's reference to "third-party apps that authenticate with your Claude subscription through the Agent SDK" ([support](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan)). "Unless previously approved" may be the reconciling clause (approved partners such as Zed/Conductor).
- OpenClaw's current docs describe a "Claude CLI (subscription reuse)" mode that "runs through the installed Claude executable on the same host" and "does not persist, refresh, or forward native login tokens." They also mark direct Anthropic OAuth-token auth as deprecated — [OpenClaw Anthropic provider docs](https://docs.openclaw.ai/providers/anthropic). This is the same pattern FlutterCraft would use.

**OpenAI**
- OpenAI's Codex for Open Source page: "Developers should code in the tools they prefer, whether that's Codex, OpenCode, Cline, pi, OpenClaw, or something else, and this program supports that work." — [Codex for OSS](https://developers.openai.com/community/codex-for-oss) (undated)

An open Codex GitHub issue requests exactly this feature — [openai/codex #10974](https://github.com/openai/codex/issues/10974)
- Codex docs recommend API keys or enterprise access tokens for automation and warn "Treat `~/.codex/auth.json` like a password" — [Codex auth](https://learn.chatgpt.com/docs/auth)
- The OpenAI Help Center article "Using Codex with your ChatGPT plan" returned HTTP 403 and could not be read — [help.openai.com](https://help.openai.com/en/articles/11369540-using-codex-with-your-chatgpt-plan)

**Google**
- The Gemini CLI ToS doc: "Directly accessing the services powering Gemini CLI (for example, the Gemini Code Assist service) using third-party software, tools, or services (for example, using OpenClaw with Gemini CLI OAuth) is a violation of applicable terms and policies." — [gemini-cli tos-privacy.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/resources/tos-privacy.md)
- Google banned paid AI Pro/Ultra subscribers who routed Gemini through OpenClaw via Antigravity OAuth, with no appeals or refunds reported (Feb 2026) — [WinBuzzer](https://winbuzzer.com/2026/02/23/google-bans-ai-subscribers-openclaw-no-refunds-xcxwbn/), [Trending Topics](https://www.trendingtopics.eu/google-blocks-paying-ai-subscribers-using-third-party-openclaw-tool/). See also Google's GitHub posts: [Discussion #22970 "mitigating abuse and prioritizing traffic"](https://github.com/google-gemini/gemini-cli/discussions/22970) and [#20632 "Addressing Antigravity Bans"](https://github.com/google-gemini/gemini-cli/discussions/20632) (not fetched)
- **June 18, 2026**: "Gemini Code Assist IDE extensions stopped serving requests for the Gemini Code Assist for individuals, Google AI Pro, and Google AI Ultra tiers." This applies to Gemini CLI too, where "Login with Google" no longer works for those tiers. Google recommends migrating to "the Antigravity family of products" (Antigravity CLI). Standard/Enterprise tiers are unaffected — [Google deprecation notice](https://developers.google.com/gemini-code-assist/docs/deprecations/code-assist-individuals)

### Inferences
- For Claude the **defensible design** is to spawn the stock `claude` binary (or the Agent SDK, which runs that binary) as the user's own local process. The user runs `claude /login` through Anthropic's flow, and FlutterCraft never touches `~/.claude` credentials or the keychain. That matches the "end user signing in to the unmodified Claude Code binary" carve-out. The residual risk: Anthropic may treat heavy parallel orchestration (many concurrent `claude -p` agents) as outside "ordinary, individual usage," and may meter or block programmatic usage later (the paused credit plan shows intent). Build the design assuming this can change on short notice.
- Using the **Agent SDK** inside FlutterCraft (instead of the CLI) is slightly riskier on paper, because the SDK overview still says no claude.ai login for third-party SDK agents "unless previously approved." Wrapping the CLI binary is better grounded in the current docs. A written clarification from Anthropic sales/partnerships would remove the ambiguity. Conductor and Zed appear to be approved partners, and FlutterCraft is not.
- Also avoid `--bare` for subscription users (it disables OAuth). Anthropic plans to make bare the default for `-p`, so the harness may need to pass explicit flags to keep subscription auth working.
- For Codex the practical risk is lower. OpenAI publicly encourages third-party tools, and app-server is designed for rich clients. Still, there is no formal ToS clause granting third-party harness use of ChatGPT plans. Spawning the official `codex` binary with the user's own login is the safe pattern.
- For Gemini, "wrap the user's consumer subscription" is **not viable** after 2026-06-18. Only API-key, Vertex, or Standard/Enterprise Code Assist users can drive Gemini CLI. The Antigravity CLI would need separate ToS review.
- Branding: do not call features "Claude Code ..." and do not mimic Claude Code visuals, per Anthropic's branding rules. This affects the Brainless-style "recreate the CLI look" idea for Claude specifically.
- None of this is legal advice. Consumer ToS text (anthropic.com/legal/consumer-terms, OpenAI Terms of Use, Google ToS) was not read in full here.

### Gaps
- I found no primary evidence of how **Conductor** technically authenticates (whether it spawns the `claude` binary with the user's login or uses the SDK with OAuth), or whether it has a formal Anthropic agreement. "Munder Difflin" returned no results in this pass.
- I could not read OpenAI's Help Center Codex-plan article (403). There is no primary OpenAI ToS clause on third-party harnesses.
- Whether Anthropic's rate limits or anti-abuse systems flag many concurrent `-p` sessions from one subscription is undocumented.
- The Anthropic Consumer Terms text itself was not fetched.
- Antigravity CLI terms and programmatic interfaces were not researched.

## (c) Flutter desktop suitability (PTY, terminals, processes, multi-window, packaging)

### Takeaway
Flutter desktop can do this, but the terminal stack is the weakest link. `xterm` 4.0.0 (last published about 2 years ago) and `flutter_pty` 0.4.2 (about 20 months ago, self-described "experimental") are effectively unmaintained, and community forks (xterm2, yoxterm) are fixing Windows ConPTY and rendering bugs. Multi-window support is experimental, on the main channel only. Packaging and auto-update are covered by community plugins (Sparkle/WinSparkle, MSIX). The native-UI-first design, which renders structured JSON events as widgets instead of emulating terminals, reduces exposure to the terminal-stack risk.

### Cited Findings
- `flutter_pty` 0.4.2, published about 20 months before Sept 2026. Platforms: Linux, macOS, Windows, Android. Describes itself as "an experimental package to explore ... native code to implement PTY instead of pure FFI and blocking isolates." 24 likes, about 6.89k downloads, MIT, publisher terminal.studio — [pub.dev flutter_pty](https://pub.dev/packages/flutter_pty)
- `xterm` (xterm.dart) 4.0.0, published about 2 years ago. It claims 60fps rendering, CJK/emoji wide chars, themes, IME, and runs on all platforms including Web. 238 likes, about 323k downloads — [pub.dev xterm](https://pub.dev/packages/xterm)
- The maintained fork `xterm2` exists "as the original package is no longer maintained" — [lohanidamodar/xterm2](https://github.com/lohanidamodar/xterm2). Another fork, `yoxterm`, adds performance/rendering fixes, including synchronized output (DEC mode 2026) — [IstiN/yoxterm](https://github.com/IstiN/yoxterm). A ConPTY fix PR notes that "ConPTY ... pad[s] the current row with spaces ... instead of sending a line break," which breaks selection and reflow — [leynier/xterm2 PR #1](https://github.com/leynier/xterm2/pull/1)
- Known upstream issues include "Major issues with the latest flutter" ([xterm.dart #207](https://github.com/TerminalStudio/xterm.dart/issues/207)), `flutter_pty.dll` failing to load with error 127 on Windows ([xterm.dart #202](https://github.com/TerminalStudio/xterm.dart/issues/202)), and input not rendering with xterm + flutter_pty ([flutter_pty #4](https://github.com/TerminalStudio/flutter_pty/issues/4))
- **Multi-window**: the Flutter Desktop Windowing API was announced **Aug 24, 2026** (Canonical-led, with Google). It supports regular, dialog, popup, tooltip, and satellite windows on Windows, macOS, and Linux, all in a single widget tree with shared state. It is **experimental**: main channel only, behind `flutter config --enable-windowing`, "subject to change." Material `showDialog` integration is not done yet — [Flutter blog](https://flutter.dev/blog/desktop-windowing-apis)
- Per a secondary source, as of Flutter 3.44.8 (Jul 23, 2026) the windowing classes are `@internal` and throw `UnsupportedError` without the flag. On stable, `desktop_multi_window` provides windows "at the cost of separate engines" — [startdebugging.net](https://startdebugging.net/2026/08/how-to-enable-multi-window-support-in-a-flutter-desktop-app/) (secondary), [pub.dev desktop_multi_window](https://pub.dev/packages/desktop_multi_window)
- **Auto-update**: `auto_updater` (leanflutter) wraps Sparkle (macOS) and WinSparkle (Windows) — [pub.dev auto_updater](https://pub.dev/packages/auto_updater), [GitHub](https://github.com/leanflutter/auto_updater). `desktop_updater` offers Sparkle-style verified updates on Windows, macOS, and Linux. On Windows it uses MSIX/App Installer APIs, and it expects macOS builds to be Developer ID signed, hardened-runtime, notarized, and stapled — [pub.dev desktop_updater](https://pub.dev/packages/desktop_updater), [hobleyd/flutter_desktop_updater](https://github.com/hobleyd/flutter_desktop_updater)

### Inferences
- **Process spawning** through `dart:io` `Process.start` (pipes, not a PTY) is enough for all the structured interfaces in section (a): stream-json, JSONL, and JSON-RPC over stdio. A PTY is only needed for an optional "raw terminal" pane, or for agent features that only work interactively. Claude agent teams, for example, need an interactive session: "In non-interactive mode with the `-p` flag, including Agent SDK sessions, Claude doesn't spawn teammates" — [agent teams docs](https://code.claude.com/docs/en/agent-teams).
- Plan to **fork or vendor** a terminal emulator (xterm2 or yoxterm) instead of depending on upstream TerminalStudio. Budget real work for Windows ConPTY edge cases.
- Rendering streaming logs and diffs: the likely bottleneck is building large `Text`/`RichText` trees for long transcripts. Virtualized lists (`ListView.builder` / slivers) and incremental syntax highlighting should keep this manageable. This is inference; I found no benchmark.
- Multi-window should not be on the critical path for v1. Use in-app panes/tabs and adopt the official windowing API when it reaches stable.
- If the core engine runs as a separate process (section d), the Flutter app mainly renders over a socket. That lowers the risk of Flutter desktop's process and PTY weaknesses, and lets the same engine serve the future web UI.

### Gaps
- I did not find a 2026 list of serious Flutter desktop developer tools with sources. Commonly cited examples (e.g., Canonical's Ubuntu desktop installer, AppFlowy, Rows, Superlist) were not verified in this pass.
- No benchmark data for Flutter rendering of high-throughput streaming text or diffs.
- MSIX packaging (`msix` pub package) and macOS notarization workflows for Flutter were not verified from primary Flutter docs.
- Whether `dart:io` has gained native PTY support by 2026 was not verified. I believe it has not (training knowledge, unverified).

## (d) Core engine language/architecture options, and orchestration patterns that work in practice

### Takeaway
The core engine has to spawn and supervise CLIs, parse NDJSON/JSON-RPC/SSE, manage git worktrees, and serve a desktop and later web UI over localhost (WebSocket or JSON-RPC). The biggest constraint is that the Claude Agent SDK exists only in Python and TypeScript, and the Codex SDK is native only in TypeScript. Every CLI can still be driven as a subprocess from any language, and ACP has Dart/Go/.NET SDKs. On orchestration, the evidence favours explicit orchestrator-worker pipelines with isolated contexts and file ownership over free-form multi-agent chat for coding.

### Cited Findings
**SDK/language constraints**
- Claude Agent SDK: Python and TypeScript only. Other languages should run `claude -p` as a subprocess — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)
- Codex SDK: the TypeScript SDK is native (`@openai/codex-sdk`) and spawns the CLI over JSONL. The Python path uses a `codex exec --json` subprocess (secondary) — [openai/codex sdk/typescript](https://github.com/openai/codex/tree/main/sdk/typescript), [hexdocs codex_sdk](https://hexdocs.pm/codex_sdk/02-architecture.html). App-server is language-agnostic JSON-RPC over stdio/WebSocket — [app-server docs](https://learn.chatgpt.com/docs/app-server)
- OpenCode: language-agnostic HTTP + OpenAPI + SSE — [OpenCode server](https://opencode.ai/docs/server/)
- ACP community SDKs exist for Dart (`acp_dart`, `dart_acp`), Go (acp-go-sdk and others), .NET, and Swift — [DeepWiki ACP community SDKs](https://deepwiki.com/agentclientprotocol/agent-client-protocol/5.6-community-sdks) (secondary), [pub.dev acp_dart](https://pub.dev/packages/acp_dart)

**Orchestration evidence**
- Anthropic's multi-agent research system (Jun 13, 2025): an orchestrator-worker setup (Opus 4 lead, Sonnet 4 subagents) beat single-agent Opus 4 by 90.2% on an internal research eval. Multi-agent runs use about 15x the tokens of chat (single agents about 4x). Token usage explained 80% of variance on BrowseComp. Anthropic warns multi-agent is a poor fit where agents "share the same context or involve many dependencies," and "most coding tasks involve fewer truly parallelizable tasks than research" — [Anthropic engineering](https://www.anthropic.com/engineering/multi-agent-research-system)
- Claude Code agent teams are **experimental**, disabled by default (`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`), and interactive-only. They use a shared task list with dependencies and file-lock claiming, plus a JSON-file mailbox per agent (`~/.claude/teams/{team}/inboxes/`). Guidance: "Start with 3-5 teammates"; "5-6 tasks per teammate"; "Two teammates editing the same file leads to overwrites"; "For sequential tasks, same-file edits, or work with many dependencies, a single session or subagents are more effective"; "Start with research and review." Hooks `TeammateIdle`, `TaskCreated`, and `TaskCompleted` (exit code 2) enforce quality gates — [agent teams docs](https://code.claude.com/docs/en/agent-teams)
- Claude Code docs point to git worktrees for running multiple sessions in parallel without automated coordination — [agent teams docs → worktrees](https://code.claude.com/docs/en/agent-teams)
- Anthropic has a post on using "dynamic workflows to orchestrate many subagents at once" — [claude.com blog: A harness for every task](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code) (linked from SDK docs; not fetched)

### Inferences
**Engine language trade-offs** (mostly inference)
- **TypeScript/Node**: first-class Claude Agent SDK and Codex SDK, the official ACP TS SDK, and `node-pty` (mature, used by VS Code). The same language can serve a web UI. It is the lowest-risk choice for agent integration. Downsides: a second runtime to bundle (or Bun/Node SEA single-binary) and a different language from the Flutter UI.
- **Python**: has the Claude Agent SDK and Codex through exec. FlutterCraft's existing TUI codebase is Python/Textual, so the team already knows it. Downsides: bundling Python (PyInstaller) and weaker PTY on Windows (`pywinpty` exists; maturity not verified here).
- **Dart** (`dart compile exe`): one language with the UI, AOT single binary, and Dart ACP SDKs. No Claude Agent SDK, so Claude Code has to be driven through `claude -p` stream-json (officially supported for non-Python/TS). PTY support depends on the weak `flutter_pty` (a Flutter plugin, not pure Dart; it may not work in a headless Dart exe). Viable if the engine uses pipes and structured protocols only.
- **Go / Rust**: excellent single-binary process supervision and PTYs (e.g., creack/pty, portable-pty used by WezTerm, not verified here), and ACP SDKs exist for Go (and a Rust SDK from Zed, not verified here). No vendor agent SDKs, so everything goes through CLI subprocesses and protocols, which is how the SDKs work internally anyway.
- A pragmatic split: the engine speaks each vendor's **wire protocol** (Claude stream-json, Codex app-server JSON-RPC, OpenCode HTTP/SSE, ACP for the long tail) instead of depending on SDKs. That makes the engine language a secondary choice. It then exposes its own versioned JSON-RPC-over-WebSocket API on localhost (with auth token) to the Flutter desktop and future web clients. The Codex app-server's capability-token WebSocket auth ([app-server docs](https://learn.chatgpt.com/docs/app-server)) and OpenCode's `127.0.0.1` + password model ([OpenCode server](https://opencode.ai/docs/server/)) are precedents.

**Orchestration**
- For coding, the evidence supports **explicit pipelines** (plan → implement → review → verify, with deterministic check steps such as `flutter analyze` / `flutter test` / `dart format` as gates) and **parallel fan-out only for independent units**, each in its own git worktree and branch, with the engine owning merges. Free-form multi-agent chat is poorly supported by the evidence for coding: Anthropic's own caveat about coding parallelism, and the agent-team warnings about same-file conflicts and the lead stopping early.
- Cross-vendor orchestration (e.g., Claude plans, Codex implements, Gemini reviews) is technically straightforward through structured handoff artifacts (plan.md, task JSON, diffs). Cost and limits multiply: about 15x tokens for multi-agent (Anthropic), and subscription limits assume "ordinary, individual usage."
- Harness-level quality gates can mirror Claude's `TaskCompleted` exit-2 hook pattern: the engine refuses to mark a task done until checks pass.

### Gaps
- I found no primary 2026 evidence comparing pipeline vs free-form multi-agent coding outcomes (e.g., SWE-bench-style studies), and no OpenAI "Codex best practices" or Imbue posts were fetched.
- The Windows PTY maturity of node-pty, pywinpty, and the Go/Rust crates was not verified with sources in this pass.
- Whether `flutter_pty` works inside a non-Flutter `dart compile exe` binary was not verified.
- How Conductor and similar tools implement worktree-per-agent and merge flows was not researched from primary sources.
