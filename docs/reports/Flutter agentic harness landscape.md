# FlutterCraft should sell verification, not orchestration

The FlutterCraft plan is sound in direction but mis-weighted in emphasis. As of September 2026, the "install and wire Google's tooling" layer is already mostly solved by Google. The official `flutter/agent-plugins` package ships skills, the Dart MCP server and hooks for Claude Code, Codex, Cursor and Antigravity. Generic multi-agent orchestration is also a commoditised category with a high death rate. The durable value sits in the gaps the plan names but treats as features: version drift, native build configuration, dependency vetting, and design/accessibility quality. None of these is covered by Google or any competitor with **deterministic, machine-checked verification**. The research also found three risks the plan did not anticipate. First, Google consumer subscriptions stopped working in Gemini CLI on 18 June 2026. Second, Anthropic changed its third-party subscription policy four times in 2026 and allows only a narrow pattern (spawning the unmodified `claude` binary with the user's own login). Third, the Flutter desktop terminal stack (`xterm`, `flutter_pty`) is effectively unmaintained. The closest direct competitor is **Vide**, a small Claude-only Flutter orchestrator with 114 stars. The research points to one architecture: a headless engine that speaks each CLI's structured wire protocol, with a Flutter desktop client added later. The right first milestone is a verifier, not a harness: a version-aware, native-config-aware check-and-fix gate that runs inside the user's existing agent before FlutterCraft orchestrates anything.

## Google already ships the wiring, so "install and connect" is a thin moat

Part of the plan assumes that setting up Flutter AI tooling for an agent is hard and unowned. By September 2026 Google owns that layer. The official Flutter docs give one-line installs for Claude Code (`claude plugin marketplace add flutter/agent-plugins`), Codex, Cursor, Copilot and Antigravity ([Flutter docs](https://docs.flutter.dev/ai/get-started)). The plugin itself is at v1.0.6 with about 3,000 stars. It bundles **10 Flutter skills, 15 Dart skills auto-synced from `dart-lang/skills`, one hot-reload rule, the `dart mcp-server` config, and format/analyze Stop hooks** ([flutter/agent-plugins](https://github.com/flutter/agent-plugins)). `package:skills` 1.0 installs skills bundled inside pub packages into each agent's folder ([dart-lang/ai skills](https://github.com/dart-lang/ai/tree/main/pkgs/skills)). Google's hosted Developer Knowledge MCP indexes docs.flutter.dev and dart.dev and aims to re-index within 48 hours ([Developer Knowledge MCP](https://developers.google.com/knowledge/reference/corpus-reference)). Google's stated principle is "open standards & agent agnostic", and the 2025 survey figure it cites is that 79% of Flutter developers use AI assistants ([Flutter blog](https://blog.flutter.dev/how-dart-and-flutter-are-thinking-about-ai-in-2026)). A harness that merely installs this is competing with a copy-paste command.

The official layer is still weaker than it looks, and those weaknesses are where a harness earns its keep. The Flutter skills are explicitly for "**happy path** Flutter development". The repo accepts no pull requests. No Flutter skill content has changed since 21 April 2026, while only tooling commits have landed ([flutter/agent-plugins](https://github.com/flutter/agent-plugins/commits/main)). One official skill is already broken: `flutter-setup-localization` writes `synthetic-package: true`, which fails on Flutter 3.47.2 ([#239](https://github.com/flutter/agent-plugins/issues/239)). The MCP server (1.1.2) is still labelled "WIP... experimental". It **disables `run_tests`, `dart_fix`, `dart_format` and the whole app-lifecycle group by default** because "agents tend to do better just using the CLI to manage the app lifecycle" ([CHANGELOG](https://github.com/dart-lang/ai/blob/main/pkgs/dart_mcp_server/CHANGELOG.md)). Yet the official integration-test skill tells agents to call the disabled `launch_app` tool. Claude Code and Codex do not auto-load the plugin's rule; users must paste it into CLAUDE.md ([dart-lang/ai #649](https://github.com/dart-lang/ai/issues/649)). The official accessibility agent exists **only in Antigravity** ([Flutter docs: tools](https://docs.flutter.dev/ai/tools)).

One planning assumption is now simply wrong. The monolithic Flutter AI rules files (`rules.md`, `rules_4k.md` and the other size variants) have been **removed**. The directory README now says guidance comes "through agent plugins and skills... instead of a single, static set of rules", and `/ai/ai-rules` redirects to the get-started page ([flutter/flutter docs/rules](https://github.com/flutter/flutter/tree/master/docs/rules)). Any design that installs those files should drop that step. One research note cited the old page as current; the primary-source check supersedes it.

| Assumed problem | Status, September 2026 | What remains for FlutterCraft |
|---|---|---|
| Wire Flutter/Dart AI tooling into agents | Solved by Google for Claude Code, Codex, Cursor, Antigravity | Pin versions, pass the right MCP `--enable` flags, patch broken skills, auto-run `skills get` on pubspec change (open issue [#585](https://github.com/dart-lang/ai/issues)) |
| Stop outdated Flutter/Dart code | Partially addressed (analyzer via MCP, `dart fix`), but no version-delta guidance | Deterministic post-edit gate plus a per-SDK delta generated from local sources |
| Correct native build/deploy config | Unaddressed by any official skill or MCP tool | Toolchain matrix checks, plugin-graph inspection, iOS lifecycle checks |
| Design, UI/UX, accessibility quality | Architecture skill exists; theming, UX and a11y absent outside Antigravity | Cross-agent a11y reviewer, design-token lints, golden/preview matrices |
| Package vs in-house vs native policy | Unaddressed beyond `pub_dev_search` | Existence/reputation/migration-status gate before `pub add` |
| Multi-agent orchestration | Commodity (worktrees, PTYs, diff review) | Reuse the pattern; do not compete on it |

## Competitors cluster at the two ends, and Vide is the one to watch

The market has split in two. At one end are hosted prompt-to-app builders for beginners. Dreamflow, from the FlutterFlow team, is the leader. Its free tier gives 10 credits, and code export and Git sit behind the **$20 and $90 monthly tiers** ([dreamflow.app](https://dreamflow.app/)). Reviewers call it better for "rapid prototyping rather than building fully-functional, production-ready apps" ([No Code MBA](https://www.nocode.mba/articles/dreamflow-flutterflow-ai)). At the other end are free "agent enhancers" that plug into the developer's own CLI. Very Good Ventures' Claude Code plugin has 14 skills, including WCAG 2.2 accessibility and a "Green Gate" verification loop, but runs **only in Claude Code** and has 165 stars ([VGV plugin](https://github.com/VeryGoodOpenSource/very_good_ai_flutter_plugin)). `mcp_flutter` (380 stars) gives agents tap, screenshot and hot-reload control of a running app ([mcp_flutter](https://github.com/Arenukvern/mcp_flutter)). Marionette MCP from LeanCode offers "Playwright MCP… but for Flutter apps" ([marionette_mcp](https://github.com/leancodepl/marionette_mcp)). FlutterCraft should compose these building blocks, not rebuild them. Google's own cloud IDE is retreating: Firebase Studio stopped accepting new workspaces in June 2026 and shuts down in March 2027 ([Firebase](https://firebase.google.com/docs/studio/migrating-project)). That leaves "bring your own agent plus official plugin" as the official path, which is the path FlutterCraft builds on.

The only product with the same thesis is **Vide**, an Apache-2.0 TUI orchestrator. It has Lead, Implementer, Code Reviewer and **Flutter Tester** roles, git worktrees, hot reload, and a vision model that "sees and taps" the app. It supports **Claude Code only** today and has **114 stars** ([vide.dev](https://vide.dev/); [GitHub](https://github.com/Norbert515/vide_cli)). The research found no evidence that Vide handles native configuration, SDK version management, beginner onboarding or accessibility audits, and no user reviews to judge its quality. `peter14l/flutter-agent-orchestrator` sketches 24 role tools (native-platform specialist, a11y auditor, and others) but has 1 star and 7 commits ([GitHub](https://github.com/peter14l/flutter-agent-orchestrator)). The claim that "Google acquired FlutterFlow in late 2025" appears only on SEO sites. No official source confirms it, so treat it as false until shown otherwise ([ortemtech](https://ortemtech.com/blog/flutterflow-review-2026-what-it-is-and-when-to-use-it/)).

Munder Difflin, the inspiration, shows both the appetite and the ceiling for generic harnesses. It reached **8.1k stars and a 312-point HN launch**, and it runs a real PTY per agent plus a git-backed "hive" for shared memory ([GitHub](https://github.com/chaitanyagiri/munder-difflin); [HN](https://news.ycombinator.com/item?id=49398152)). HN commenters still called the Office-themed UI "too cute" and asked for "a more utilitarian view". They also doubted that agents with "personalities pursuing... little goals" produce anything but dysfunction ([HN](https://news.ycombinator.com/item?id=49398152)). The wider category is brutal. Terragon shut down in February 2026 for "insufficient traction". Crystal was deprecated the same month, Vibe Kanban's parent Bloop shut down in April, and Omnara pivoted to enterprise ([agentsroom](https://agentsroom.dev/blog/best-multi-agent-coding-tools); [Munder blog](https://munderdiffl.in/blog/best-claude-code-multi-agent-tools/)). Claude Code now ships native (experimental) Agent Teams ([Claude Code docs](https://code.claude.com/docs/en/agent-teams)). Worktree-per-agent orchestration is therefore a feature the agent vendors are absorbing, not a moat. The Go TUI Sidecar (1.1k stars) is the closest UX benchmark for FlutterCraft's current Textual TUI ([Sidecar](https://github.com/marcus/sidecar)).

| Tool | Flutter-specific | Multi-agent | Agents supported | Traction (Sep 2026) |
|---|---|---|---|---|
| Vide | Yes (Flutter Tester, hot reload, vision) | Yes | Claude Code only | 114 stars |
| VGV AI plugin | Yes (14 skills, Green Gate) | Reviewer subagent only | Claude Code only | 165 stars |
| flutter/agent-plugins | Yes (happy path) | No | Claude, Codex, Cursor, Antigravity | ~3,000 stars |
| mcp_flutter / Marionette | Runtime control | No | Any MCP client | 380 / ~467 stars |
| Dreamflow | Yes, hosted | No | Vendor models | "2M+ builders" (self-reported) |
| Munder Difflin | No | Yes (hive, orchestrator) | 12+ CLIs | 8.1k stars |
| Sidecar, Claude Squad, Conductor | No | Session/worktree managers | Multi-CLI | Sidecar 1.1k stars |

## Version and native-build drift are the deepest, least-served gaps

Stale code is a real problem, and it gets worse with each release. The current stable is **Flutter 3.47.5 / Dart 3.13.4 (18 September 2026)**. There have been **ten quarterly minors since Flutter 3.19**, so a model trained on 2024 data is 8–11 releases behind ([releases_linux.json](https://storage.googleapis.com/flutter_infra_release/releases/releases_linux.json)). The next jolt is imminent. Material and Cupertino moved into standalone `material_ui` and `cupertino_ui` packages, and the old imports are "scheduled for formal deprecation in the Fall stable release (November)" ([Flutter 3.47](https://flutter.dev/blog/whats-new-in-flutter-3-47)). That puts a deprecation warning on the most common line in Flutter code, `import 'package:flutter/material.dart';`, which every agent will keep regenerating. Dart has also added dot shorthands (3.10), private named parameters (3.12) and primary constructors (3.13), while macros were cancelled ([Dart language evolution](https://dart.dev/resources/language/evolution)). Agents under-use new syntax and hallucinate cancelled syntax. New syntax is also gated by the pubspec SDK lower bound, so the harness must tell the agent the *language version*, not just the installed SDK.

The research also shows *how* to fix this, and the answer favours deterministic tooling over prompting. In the ICSE 2025 study of deprecated-API use across 7 LLMs, direct replacement (REPLACEAPI) fixed **over 85%** of deprecated usages. Adding deprecation hints to the prompt "does not currently achieve sufficient effectiveness". The model's output was also steered by whether the surrounding code was old or new ([arXiv 2406.09834](https://arxiv.org/pdf/2406.09834)). In a legacy project full of `withOpacity`, the agent will keep writing `withOpacity` whatever the CLAUDE.md says. GitChameleon found top models solve only **48–51%** of version-conditioned tasks, and retrieval adds at most about 10% ([arXiv 2507.12367](https://arxiv.org/abs/2507.12367)). The Flutter equivalents are already on the user's disk. `dart fix` is driven by `fix_data` YAML that ships inside every Flutter SDK install ([fix_data README](https://github.com/flutter/flutter/blob/master/packages/flutter/lib/fix_data/README.md)). The analyzer flags `deprecated_member_use`. The releases manifest maps each Flutter version to its date and Dart version. FlutterCraft can generate an exact, offline, per-SDK "version delta" and enforce it with a post-edit gate. Nobody ships that today, and no Flutter-specific benchmark measures the problem (FlutterBench is "coming soon" ([flutter/website](https://github.com/flutter/website/tree/main/sites/docs/src/content/ai/flutter-bench))). An eval would double as FlutterCraft's proof of value.

Native build configuration is the biggest gap, because `dart fix` never touches Gradle or Xcode and no official skill or MCP tool covers it. Android is mid-migration. Flutter 3.47's template baseline is **Java 17, AGP 9.1.0, Gradle 9.3.1, KGP 2.4.0, SDK 36, minSdk 24** ([Flutter 3.47](https://flutter.dev/blog/whats-new-in-flutter-3-47)). AGP 9 defaults to built-in Kotlin, and "apps fail to build if they use unmigrated Flutter plugins that still apply" KGP ([Flutter docs](https://docs.flutter.dev/release/breaking-changes/migrate-to-built-in-kotlin/for-app-developers)). An open P1 bug means enabling built-in Kotlin on AGP 9.3+ fails Flutter's own Kotlin version check ([#192167](https://github.com/flutter/flutter/issues/192167)). The newest AGP, 9.4, needs Gradle 9.6. Flutter's source lists 9.5.0 as its maximum known Gradle, so **AGP 9.4 is effectively unsupported with Flutter today** ([AGP notes](https://developer.android.com/build/releases/gradle-plugin); [gradle_utils.dart](https://raw.githubusercontent.com/flutter/flutter/master/packages/flutter_tools/lib/src/android/gradle_utils.dart)). An agent that "helpfully" upgrades AGP to latest will break the build. Google Play has required **targetSdk 36 for new apps and updates since 31 August 2026**, with extensions only to 1 November ([Play Console Help](https://support.google.com/googleplay/android-developer/answer/11926878?hl=en)).

iOS has its own set of deadlines:

- **SwiftPM** has been the default since Flutter 3.44.
- **CocoaPods trunk** goes permanently read-only on **2 December 2026** ([CocoaPods blog](https://blog.cocoapods.org/CocoaPods-Specs-Repo/)).
- **Minimum targets** are now iOS 15 and macOS 12 in Flutter 3.47. The Flutter deployment docs still say iOS 13 ([Flutter iOS deployment](https://docs.flutter.dev/deployment/ios)), so doc-reading agents will get this wrong.
- **UIScene:** building with Xcode 27 makes the UIScene lifecycle mandatory, and "Flutter apps that haven't adopted it will crash on startup". Only apps with an unmodified AppDelegate migrate automatically ([Flutter UIScene](https://docs.flutter.dev/release/breaking-changes/uiscenedelegate)). The apps at risk are the ones using Firebase, push notifications, deep links or method channels.

**Nobody publishes a machine-readable compatibility matrix.** The closest thing is Flutter's own `gradle_utils.dart`, versioned per SDK tag and present in the local SDK. It encodes template versions, "max known" versions and Java↔Gradle↔AGP tables ([gradle_utils.dart](https://raw.githubusercontent.com/flutter/flutter/master/packages/flutter_tools/lib/src/android/gradle_utils.dart)). The practical lesson is that **a Flutter app's native build is the union of the app's config and every plugin's config**. The tool that wins inspects the plugin graph in the pub cache and orchestrates Flutter's own migrators (`flutter analyze --suggestions`, `--config-only` builds). It does not hand-write Gradle files. Existing community tools such as `flutter_flavorizr` admit they work "better on a new and clean Flutter project" ([pub.dev](https://pub.dev/packages/flutter_flavorizr)). Some deployment steps are one-way doors: the application ID "cannot change after the first Play upload", and a lost upload keystore is unrecoverable without Play App Signing ([Flutter Android deployment](https://docs.flutter.dev/deployment/android)). These belong behind explicit human confirmation, especially for beginners.

## Dependency and design policies work only when backed by checks

The proposed dependency policy holds up, with three amendments: small helpers in pure Dart, well-maintained packages for complex platform features, native code only as a last resort. First, "well-maintained" needs a machine-checkable definition, because every plugin carries two forced migrations in 2026–27. Only **61% of the top 100 iOS plugins had migrated to SwiftPM by 30 April 2026** ([Flutter blog](https://flutter.dev/blog/saying-goodbye-to-cocoapods-swift-package-manager-is-soon-the-default-in-flutter)). That rose to 92 by the 3.47 release ([Flutter 3.47](https://flutter.dev/blog/whats-new-in-flutter-3-47)). Popular plugins such as `wakelock_plus` and `flutter_tts` still had open built-in-Kotlin issues ([wakelock_plus #117](https://github.com/fluttercommunity/wakelock_plus/issues/117)). Even Google-published packages get discontinued, as `flutter_markdown` was in 2025 ([flutter/flutter #162966](https://github.com/flutter/flutter/issues/162966)). A stale community plugin for a small feature can be worse than a 50-line Pigeon wrapper.

Second, every proposed package must be checked for existence before `pub add`. Package hallucination appeared in **at least 5.2% of commercial-model and 21.7% of open-source-model samples**, across 205,474 unique invented names ([USENIX Security 2025](https://arxiv.org/abs/2406.10279)). Hallucinated names also repeat across runs, which is what makes "slopsquatting" attacks viable ([Socket](https://socket.dev/blog/slopsquatting-how-ai-hallucinations-are-fueling-a-new-class-of-supply-chain-attacks)). No pub.dev-specific incident was found, but the mechanism does not depend on the ecosystem.

Third, "write native code" should default to **Pigeon**, which the official docs present as the type-safe path ([Flutter platform channels](https://docs.flutter.dev/platform-integration/platform-channels)). jnigen (`jni` 1.0) is usable on Android. swiftgen is "still not stable", and one practitioner wrote his guide specifically because AI agents got it wrong ([Roszkowski](https://roszkowski.dev/2026/swiftgen-jnigen/)). The official architecture guide backs a small endorsed set of packages (provider, go_router, freezed) and warns that codegen adds build time ([Flutter architecture](https://docs.flutter.dev/app-architecture/recommendations)). That fits the "pure Dart for small things" half of the policy.

Design, UI/UX and accessibility is a genuine gap, but only if FlutterCraft pairs guidance with verification. The official skills have no theming, design-system, UX-state or accessibility skill. Accessibility is an open P1 request ([#101](https://github.com/flutter/agent-plugins/issues/101)). Material 3 Expressive and iOS 26 Liquid Glass have **no official Flutter implementation**, only "work... underway" in the new packages with no date ([Flutter blog](https://flutter.dev/blog/decoupling-material-cupertino)). Agents therefore need to be told explicitly that community packages here are an opt-in dependency risk.

Several building blocks for deterministic checks already exist. `flutter_test` ships `meetsGuideline` matchers for tap targets, labels and text contrast ([Flutter a11y testing](https://docs.flutter.dev/ui/accessibility/accessibility-testing)). Dart 3.10 added first-party analyzer plugins, replacing the archived `custom_lint`. Their diagnostics appear in `dart analyze` ([dart.dev](https://dart.dev/tools/analyzer-plugins)), so FlutterCraft-authored rules (layer imports, token-only colours and spacing, no orientation locks, labelled images) would reach every agent. Widget Previews went stable in 3.47 and accept brightness, text-scale and localisation parameters ([Flutter docs](https://docs.flutter.dev/tools/widget-previewer)). Rendering those as goldens gives any agent a headless way to "see" light/dark, 2× text and RTL variants.

Community skills found for design are static prose. The best known, `hamen/material-3-skill` (about 1.4k stars), targets Jetpack Compose first ([GitHub](https://github.com/hamen/material-3-skill)). Combining guidance with generated tests and lints is the open space. One limit stays: golden diffs detect change, not quality. Aesthetic judgement and screen-reader flow still need AI or human review.

## The architecture evidence favours a headless engine that speaks wire protocols

**Terms of service shape the design more than any technical choice.** Anthropic's current legal page says developers "may not collect, store, or intermediate Claude.ai credentials". It explicitly permits "an end user... signing in to the unmodified Claude Code binary with their own Claude subscription", provided the product does not modify the binary, "remove... any authentication method" or resell usage ([Claude Code legal](https://code.claude.com/docs/en/legal-and-compliance)). That page followed a volatile year: a ban on third-party subscription use in February and April, a reinstatement with a metered credit in May, and a pause on that credit in June ([VentureBeat](https://venturebeat.com/technology/anthropic-reinstates-openclaw-and-third-party-agent-usage-on-claude-subscriptions-with-a-catch); [Claude Help Center](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan)). The page also says usage limits "assume ordinary, individual usage" and that enforcement may come "without prior notice". Heavy parallel fan-out on one subscription is therefore the riskiest thing FlutterCraft could do. The Agent SDK is on shakier ground than the CLI: its overview still bars third-party claude.ai login "unless previously approved" ([Agent SDK](https://code.claude.com/docs/en/agent-sdk/overview)).

The Gemini assumption is broken. Since **18 June 2026**, Google AI Pro/Ultra and Code Assist for individuals no longer serve Gemini CLI, and Google points users to Antigravity ([Google deprecation notice](https://developers.google.com/gemini-code-assist/docs/deprecations/code-assist-individuals)). Google also banned paying subscribers who routed Gemini OAuth through third-party tools ([WinBuzzer](https://winbuzzer.com/2026/02/23/google-bans-ai-subscribers-openclaw-no-refunds-xcxwbn/)). OpenAI is the most permissive in practice: "Developers should code in the tools they prefer... OpenCode, Cline, pi, OpenClaw" ([Codex for OSS](https://developers.openai.com/community/codex-for-oss)). It has no formal clause granting harness use, though. The defensible rule for every vendor is to spawn the stock binary, let the vendor's own login flow run, and never touch tokens. The Antigravity CLI (`agy`) was not researched and needs its own terms review before FlutterCraft supports it.

Two Claude-specific traps follow from this. A `claude -p` session runs the repo's `.claude/settings.json` hooks and `.mcp.json` servers "even in a folder you've never trusted". The harness therefore needs its own trust prompt before launching agents in a new repo. Separately, Anthropic plans to make `--bare` the default for `-p`, and `--bare` does not read OAuth credentials, which would silently break subscription users ([Claude Code headless](https://code.claude.com/docs/en/headless)).

The good news is that PTY scraping is no longer necessary. Every target CLI now has a structured interface:

| Agent | Structured interface |
|---|---|
| Claude Code | `-p --output-format stream-json`, with subagent nesting, cost and a `capabilities` array for feature detection |
| Codex | `codex app-server`, JSON-RPC 2.0 with approvals and `turn/steer` ([Codex docs](https://learn.chatgpt.com/docs/app-server)) |
| Gemini CLI | stream-json output |
| OpenCode | An HTTP/OpenAPI server with server-sent events ([OpenCode](https://opencode.ai/docs/server/)) |
| Long tail | ACP covers about 40 agents and has Dart SDKs ([ACP agents](https://agentclientprotocol.com/get-started/agents)) |

ACP reaches Claude and Codex only through third-party adapters that flatten their features. The evidence therefore supports **native adapters for Claude and Codex, and ACP for the rest**. Because the ToS analysis already pushes FlutterCraft to spawn CLI binaries rather than embed vendor SDKs, the engine language stops mattering much. The Claude Agent SDK is Python/TypeScript-only, and the docs tell other languages to use `-p` ([Agent SDK](https://code.claude.com/docs/en/agent-sdk/overview)). A Dart engine (`dart compile exe`) is viable over pipes and would share a language with the UI and with the analyzer-plugin and `fix_data` tooling the verifier needs. The existing Python codebase is also viable. TypeScript has the most vendor SDKs but adds a runtime.

**Flutter desktop is suitable as a client, not as the process supervisor.** `xterm` 4.0.0 and `flutter_pty` 0.4.2 have not been published in about two years, and forks exist "as the original package is no longer maintained". There are open Windows ConPTY and DLL-loading bugs ([pub.dev xterm](https://pub.dev/packages/xterm); [xterm2](https://github.com/lohanidamodar/xterm2); [xterm.dart #202](https://github.com/TerminalStudio/xterm.dart/issues/202)). The new desktop multi-window API is experimental and main-channel only ([Flutter blog](https://flutter.dev/blog/desktop-windowing-apis)). A separate engine exposing authenticated JSON-RPC over a localhost WebSocket keeps those weaknesses off the critical path. It lets the Flutter app render structured events as native widgets, with a raw terminal only as a debug fallback. The same engine can also serve the current TUI and a future web client. If FlutterCraft recreates CLI visuals, Anthropic's branding rule forbids mimicking Claude Code's look or using its name in the product name.

On orchestration, the evidence argues against a Munder-style "office". Anthropic's multi-agent research system beat a single agent by 90.2%, but it used about **15× the tokens of chat**. Anthropic warns that "most coding tasks involve fewer truly parallelizable tasks than research" ([Anthropic engineering](https://www.anthropic.com/engineering/multi-agent-research-system)). Claude's own Agent Teams docs say two teammates editing one file overwrite each other. For sequential or same-file work, they say, "a single session or subagents are more effective" ([Claude Code docs](https://code.claude.com/docs/en/agent-teams)). The pattern that fits Flutter work is an explicit pipeline: plan, implement, review, verify. Deterministic gates (`dart format`, `dart fix`, analyze, tests, `--config-only` builds) refuse to mark a task done. Parallel worktrees should be reserved for genuinely independent units.

## Conclusion

The research changes FlutterCraft's centre of gravity. Orchestration and tool installation turned out to be the least defensible parts of the plan: Google gives the wiring away, vendors are absorbing orchestration, and five orchestrators died or pivoted in ten months. The parts that looked like secondary features turned out to be the product: version deltas, native-config sanity, package vetting, and accessibility and design gates. They are hard, Flutter-specific, and backed by evidence that deterministic checks beat prompts. They also sit on local, authoritative data (`fix_data`, `gradle_utils.dart`, the releases manifest, the plugin graph) that a generic tool will never parse. A verifier is also the design most robust to vendor policy swings. It runs inside whatever agent session the user already pays for, so FlutterCraft never intermediates a subscription. For beginners, "you own the code from minute one, and it builds for the stores" is a sharper pitch against Dreamflow's paywalled export than any visual metaphor.

The first milestone should therefore be a headless `fluttercraft verify` engine, shipped as a Claude Code/Codex plugin with a post-edit hook and no orchestration yet. It should:

- detect the SDK via FVM, along with the pubspec language version;
- install and pin the official plugin, with the right MCP `--enable` flags and patches for known-broken skills;
- emit a compact per-SDK version delta;
- fail on `deprecated_member_use` after running `dart fix`;
- audit Android and iOS config against the local `gradle_utils.dart` and the plugin graph, covering KGP application, namespace, SwiftPM status, targetSdk 36, UIScene and secrets in git;
- gate `pub add` on existence and maintenance checks.

Measure it with a small Flutter version-drift eval, since no public one exists, and publish the numbers. Only after that gate is trusted should milestone two wrap Claude and Codex in a single-agent pipeline through their structured protocols. The Flutter desktop client and parallel agents come third, once there is something worth orchestrating. Three questions stay open: Anthropic's next policy move, Vide's real quality, and whether the Antigravity CLI's terms permit wrapping. Revisit all three before each milestone.
