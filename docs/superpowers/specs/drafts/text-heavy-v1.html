The Einstein of app development.

Appstein gives AI coding agents what they lack when they build Flutter apps: accurate, current knowledge of the SDK and the project, and a strict check on everything they write.

Flutter 3.44+ · Dart Claude Code · Codex Android + iOS first open source
Apps = m·c²
m = a model that is already smart
c = context, current and exact
c again = checks that never skip
The idea

Guide the agent before it writes. Check it after.

Agents don't need to be smarter. They need to stop guessing. Research found that telling a model about deprecated APIs is not enough, but fixing them automatically after generation works in over 85% of cases. So Appstein does both.

1

Outdated code. Models were trained 8 to 11 Flutter releases ago and keep writing withOpacity, WillPopScope and the old material.dart import.

2

Wasted tokens. Every session starts with the agent searching the repo to rebuild a mental map it already built yesterday.

3

Broken native builds. 2026 brings AGP 9 built-in Kotlin, SwiftPM by default, CocoaPods going read-only on Dec 2, and UIScene with Xcode 27.

4

Bad packages. Models invent package names in 5 to 22% of samples and pick plugins that no longer build.

Before writing · guide

A knowledge layer that can't go stale

  • Generated from the installed SDK and the analyzed code
  • Served as plain files plus an MCP server agents can query
  • Only a small index is always loaded; details on demand
After writing · check

A verifier that blocks "done"

  • Analyzer, dart fix, and our own lint rules after every edit
  • Native Android and iOS config audit and real builds
  • A package gate before any dependency is added

Knowledge layer

Four layers. Two generated, two written and checked.

Stale knowledge is worse than none, because agents trust it. So anything that can be generated is generated, and anything written by hand is checked against the code.

1

Flutter platform knowledge

Installed SDK and language version, "use X, not Y" for this exact SDK, and the valid native toolchain set. Built from the SDK's own fix_data, releases list and gradle_utils.dart.

generated
2

Project map

Features, screens, view models, repositories, routes, layer imports, packages and native config. Built by the Dart analyzer, so it's exact, and refreshed after every edit.

generated
3

Project decisions

Why things are the way they are: architecture, state management, tokens, conventions. The verifier flags a decision that no longer matches the code.

written · checked
4

Work memory

The task in progress, what was tried, lessons learned. Tidied up when a task ends.

written · checked

MCP tools: agents ask instead of searching

Google's Dart MCP server runs alongside for the analyzer, hot reload and pub.dev search. Exactly one copy runs, and we don't duplicate its tools.

The loop

What happens while an agent works

In Milestone 1 the user runs their own Claude Code or Codex. Appstein only configures the project, so it never touches logins or credentials.

The agent needs context
reads INDEX.mdasks MCP where_is / featuregets exact files

No repo-wide searching, so fewer tokens.

After every change · seconds
detects changed files (edits and Bash)analyze + our lint rulesreports only, never rewrites
pass → continuefail → findings to agent
When it says "done" · slower
dart fix + format (safe now)all tests + Android/iOS auditreal debug build
pass → doneerrors → "done" blocked

A session-start hook builds the knowledge first. Fast checks never touch files mid-session, because rewriting a file the agent just read makes its next edit fail. If the same errors block "done" three times in a row, Appstein stops blocking and hands the list to you, so the agent can't loop and burn tokens.

The agent can't mark a task done while errors remain. That's the whole trick.

Verifier

Checks that run by themselves

Fast · after every change · report only

  • dart analyze fails on any deprecated API
  • Pending dart fix and format changes listed
  • No UI code importing the data layer
  • Colors and spacing only from theme tokens
  • No Platform.isX layouts, no orientation locks
  • Knowledge is fresh (hash check)

Full · when the agent says done

code
  • flutter test, including tap-target, label and contrast checks
android
  • Gradle, AGP, Kotlin, JDK inside the valid set; SDK levels via Flutter's variables, targetSdk ≥ 36
  • No plugin breaking AGP 9 built-in Kotlin; minSdk fits every plugin
  • 16 KB page-size alignment for native libraries
  • No signing or store secrets in git; quick config-only build, then a real flutter build apk --debug
ios (static on Windows, real build on Mac CI)
  • iOS 15+ everywhere; SwiftPM on; UIScene and privacy manifests present
  • Usage descriptions for every permission a plugin needs
packages
  • Package exists, isn't discontinued, is maintained, builds on 2026 toolchains

Dependency policy: taught by a skill, enforced by the package gate

Small helper

Formatting, validation, simple state, HTTP wrapper.

→ write it in pure Dart

Complex platform feature

Camera, permissions, notifications, payments, maps, auth.

→ well-maintained package

Small native feature, no good package

Rare, and only when needed.

→ Pigeon + platform channels

appstein create

A new project that builds on the first try

  1. Preflight. Doctor checks the machine. You confirm the organization and app ID, since these are permanent after the first store upload.

  2. Base. Runs flutter create for Android and iOS.

  3. Structure. Flutter's official architecture: ui/<feature>, data/, domain/, routing/, with go_router, provider, light and dark themes and design tokens. On Flutter 3.47+ it uses the new material_ui package.

  4. Native config. Sets Android and iOS to the valid toolchain for your SDK: SwiftPM, UIScene and privacy manifests included.

  5. Sample feature. One screen with view model, repository, fake and tests, including accessibility tests.

  6. Finish. Sync, set up agents, run the full verify. It must pass. Git is initialized, and nothing is committed without you.

appstein upgrade keeps projects current later: one migration folder per Flutter version, previewed with --dry-run, using Flutter's own migrators wherever possible.

Done when: create → verify passes on Linux and macOS CI, and the benchmark shows zero deprecated APIs and a higher verify pass rate with Appstein than without. Token use is reported honestly either way.

M2next

Single-agent pipeline harness

Appstein drives the official CLIs through their structured output: plan → build → review → verify, with hard gates. You always log in through the vendor's own flow.

M3then

Existing projects + more stacks

Adopt apps that already exist. Riverpod and Bloc packs. Community packs.

M4later

Flutter desktop app + agent team + every platform

A native UI for agent activity, parallel agents for independent work, web and desktop platform packs, then a web UI.

How we'll prove it works

10 to 20 realistic tasks run by Claude Code with and without Appstein, on a fresh app and on a legacy app full of old APIs. We measure tokens, turns, deprecated APIs left, verify pass rate, build success and time, and publish the numbers.

Risks and open questions

What we're watching

Vendor policy changes

Anthropic changed its rules four times in 2026. M1 runs no agents, so no exposure. Re-check before M2.

Codex hook support

Unverified. If missing, Codex calls verify through MCP and CI enforces it.

Material moving packages

The old import is deprecated in the November stable. The version delta and an upgrade migration handle it.

Competitor: Vide

Flutter multi-agent tool, Claude only, small. Our edge is exact knowledge, verification and support for more agents.

Name and brand

Trademark and domain check before the first public release. Einstein pun only, never his likeness.

Firm product or not

Decide after the M1 benchmark. It sets the license and where the repo lives.

iOS on Windows

Static checks locally, real iOS builds on macOS CI.

Minimum Flutter version

Proposed 3.44+, because the Dart MCP server needs Dart 3.12. Confirm in slice 1a.

Glossary

Terms used in this plan

Agent CLI
A command-line AI coding tool, such as Claude Code or Codex.
MCP
A standard way for agents to call outside tools. Our server lets agents ask Appstein questions.
Skill
A short instruction file an agent loads when a task needs it.
Hook
A command the agent tool runs automatically, for example after an edit or before stopping.
Analyzer
Dart's own engine for understanding code exactly, which makes our project map precise.
fix_data
Files in the Flutter SDK that map deprecated APIs to their replacements. dart fix uses them.
Pack
A plug-in bundle of knowledge, checks, rules and templates for one stack or one platform.
Toolchain matrix
The Gradle, AGP, Kotlin, JDK and SDK versions known to work together for a Flutter version.
Pub workspace
A Dart feature that lets one repo hold several related packages.
Golden test
A test that compares generated output with a saved, approved copy.
